# FCC intelligent context management design

## Intent

Reduce repeated input tokens in long FCC conversations while retaining task continuity, user instructions, tool protocol validity, and the original history. Context optimization applies to each outbound model request, including provider retries, stream continuations, internal web-search decisions, native Messages passthrough, and requests from native Claude/Codex clients routed through FCC.

## Diagnosis of the current flow

### History and persistence

- The regular `/v1/messages` and `/v1/responses` routes accept a complete request from the client on each turn. The proxy does not reconstruct ordinary API history from SQLite; each client chooses and resends its conversation.
- `/v1/messages` restores entries encoded by `api/compact_history.py`. That helper recognizes a Claude compaction marker and prepends its saved turns. It is a replay-compatibility mechanism, not token-budget management, and can make the request larger.
- The Messages and Responses models preserve provider-specific/unknown fields. Responses inputs can also contain provider-native items and references such as `previous_response_id`; their context may not be fully visible to FCC.
- The code-session SQLite tables retain UI items, runs, prompts, and usage. The native Claude Agent SDK resumes its own session/thread and sends only the new prompt through the worker; SQLite is not the transcript source for those calls. The SDK is configured to use FCC's local Anthropic proxy, so its actual upstream HTTP requests can be controlled there.
- Tool calls and tool results are represented in provider-specific message blocks/items. Replay validation and history normalization already protect some signatures and ordering. Tool outputs can include large text, structured values, and media. Files and attachments may be represented as user text/path references, while the native agent can read files through its own tools.

### Existing limits and provider boundaries

- Existing token estimators support Anthropic Messages and OpenAI Responses, with approximate text tokenization and imperfect image/non-OpenAI estimates. They are for accounting; there is no shared configurable input budget or context compaction before sending.
- `ProviderExecutor` estimates some regular Messages/Responses requests, but provider transports can add or repair history during retries and continuations. Native Messages passthrough has a separate HTTP path. Enforcement only in the executor would miss those final payloads.
- Most providers share three transports: Anthropic Messages, OpenAI Chat Completions, or OpenAI Responses. Gemini and Vertex in this checkout use the OpenAI-compatible Chat path. OpenAI-compatible wrappers and several provider adapters reuse those transports. Direct native Messages passthrough and custom/native provider branches need explicit coverage checks.
- Providers return different usage shapes. Existing stream parsers already expose actual input, cached input, output, and reasoning usage for several protocols; estimates must remain labeled as estimates until actual usage arrives.
- The shared OpenAI Chat parser reads `prompt_tokens_details.cached_tokens`, but currently converts an absent cache count to `0` in its normalized usage event. That loses the distinction between a confirmed zero and a provider that did not report the field; diagnostics must retain “unknown” separately even if the existing public response contract needs a numeric fallback.
- Prompt-cache behavior is provider-specific. Anthropic supports stable-prefix caching controls; OpenAI-compatible APIs can report cached input where supported; Gemini and Vertex have implicit and explicit context-caching features on their native APIs. FCC's current Gemini/Vertex Chat-compatible transports do not create Google context-cache resources. The selected extension keeps invariant prefixes stable for implicit caching everywhere and adds native explicit Google caching for eligible Gemini/Vertex requests, with the existing Chat-compatible path as fallback.

## Approaches

1. **Implicit cache optimization only.** Preserve identical stable prefixes, append changing turns at the end, and rely on provider automatic caching. It has no cache creation/storage charge but offers no guarantee that a prefix is retained or reused.
2. **Explicit Google cache only.** Create/reuse Google `CachedContent` references for Gemini/Vertex. This gives explicit TTL and reuse but requires native API integration, model eligibility checks, lifecycle handling, and cost accounting; changing cached content can require a full-price recreation.
3. **Combine both.** Preserve invariant prefixes across providers and create/reuse explicit native Google caches for eligible Gemini/Vertex requests. Send changing turns after the cached content; keep the current OpenAI-compatible Chat flow when native caching is unsupported or fails safely. This keeps automatic prefix reuse available in the fallback and other providers, while allowing controlled reuse on Google. **Selected by the user.**

## Goals

- Apply a configurable input budget before every upstream generation request.
- Preserve stable instructions, current user requests, recent turns, complete tool-call/result groups, and opaque provider state that cannot safely be reconstructed.
- Summarize older completed conversation spans into structured state, leaving persisted and client-owned original histories untouched.
- Reduce repeated tool output and represent oversized outputs with faithful excerpts/references only where a real retrieval path exists.
- Expose estimated and provider-reported token metrics, compaction savings, message counts, and internal summarization calls.
- Keep provider cache semantics and message wire formats intact, with a native Google adapter for explicit context caching.

## Non-goals

- Rewriting client or SQLite transcripts.
- Claiming exact token counts for models/modalities without an exact provider tokenizer.
- Creating provider-native cache objects in generic Chat-compatible paths; explicit Google caching is isolated to the native Google adapter.
- Changing agent reasoning, tool permissions, or user-visible conversation behavior beyond explicit budget errors and diagnostics.
- Compacting opaque `previous_response_id` context that FCC cannot inspect.

## Proposed design

### Boundary and protocol adapters

Add one context manager under the application/core layer and a small hook at each final send point. The hook accepts the fully assembled outbound body plus protocol/provider/model metadata and returns a body plus a request-scoped measurement. Adapters cover Anthropic Messages, OpenAI Chat Completions, and OpenAI Responses. Invoke it after retry/continuation/history repair and immediately before each network send, including native Messages passthrough. Internal web-search model requests and summary calls pass through the same budget check. Unsupported opaque/native paths remain unchanged but emit a diagnostic that enforcement was unavailable; they must not be silently described as budgeted.

Provider conversions retain the existing stable system/developer instructions and tool schemas at the front, then the compacted conversation in chronological order, followed by the untouched recent tail. Do not reorder provider-owned reasoning/signature fields. Treat tool-call/result groups and any associated signatures atomically. Preserve cache-control fields and provider extensions on stable prefixes.

### Implicit and explicit Google caching

Cache optimization is additive, not a reason to reorder or weaken context. Across all providers, keep large invariant instructions/tool definitions and a reusable compacted checkpoint byte-identical at the front; append each new turn and other changing content after that prefix. Avoid injecting timestamps, per-request diagnostics, or reconstructed equivalent JSON into the stable region. A provider-reported cache hit is the only evidence of implicit-cache reuse; implicit entries may be evicted early and their published maximum lifetime (up to 24 hours for Vertex) is not a retention guarantee. Preserve actual cached-token usage as reported and never predict implicit-cache savings as actual billing savings.

For eligible Gemini Developer API and Vertex models, add a Google-native `generateContent` adapter capable of creating and referencing `CachedContent`. The immutable cache consists only of the stable portion supported by the model/API (system instruction, tools, and/or a complete stable contents prefix); turn-specific content is appended to the generation request. When a request references a cache, do not also serialize the cached contents inline: send only the uncached dynamic suffix and verify the split against the cached-prefix digest to prevent duplicate token transmission/billing. Cache scope includes provider, endpoint/project, model, authorization principal, and a trustworthy opaque user/session scope so cached data is not reused across tenant or permission boundaries. If an API request has no stable session identity, do not use explicit caching for it; preserve the generic/fallback flow. Persist only the opaque Google cache resource name, a keyed scope/prefix digest, model/project identifiers needed for routing, creation/expiry metadata, and cost/usage counters; never persist raw prompts, credentials, or raw session IDs. Keep this registry bounded and remove/expire stale entries.

The Google adapter must preserve the current FCC outward stream contract, tool calls, reasoning fields where supported, usage metrics, cancellation, retries, and error mapping. Determine explicit-cache eligibility from current model/API capability and minimum-token requirements; do not hard-code assumptions based only on a model name list. A native request is used only when its full behavior can be represented safely. Unsupported models, under-minimum prefixes, cache lifecycle/API errors, or unsupported request features fall back to the current OpenAI-compatible request. Fallback must retain stable-prefix ordering and report the reason without logging prompt content.

Cache lifecycle is incremental and economic: reuse an exact matching unexpired prefix; do not rewrite it for each new turn. When the reusable prefix has changed or an uncached suffix becomes too large, compare the estimated cost of a full-price cache creation plus storage TTL against expected cached-token reuse and the ordinary implicit-cache/fallback path. Cache creation and storage are initially disabled. First collect at least seven days of real Gemini/Vertex implicit-cache hits and uncached input across repeated calls, with at least 100 eligible requests per provider/model; if volume is lower, keep creation disabled until the minimum is met. The current Admin usage store does not retain a stable-prefix digest, so phase one adds a keyed digest and eligible-prefix token estimate without prompt text or raw session IDs. Once actual cached/uncached usage and published model/storage prices show projected net savings for that workload, the policy may enable creation automatically; insufficient samples, unknown required pricing, or a non-positive projection keeps it disabled. Google Billing/SKU reports are used to reconcile aggregate cost when available, but are not a prerequisite for the projection. An operator setting can disable creation at any time and tune the minimum projected savings. Thereafter create/roll forward only when configured policy predicts net savings; otherwise keep the existing cache and send the rest as suffix or fall back. Make TTL, eligibility/minimum size policy, and the minimum projected savings configurable. Do not promise a fixed 90% net reduction: cache writes, storage, model pricing, and reuse count affect the break-even point. Record actual token quantities and cache lifecycle events; calculate storage cost from cache token count, TTL, and the current published rate, label it as an estimate, and reconcile aggregate totals against Google Billing/SKU data when available. Show realized savings separately from estimates.

### Budget and estimation

Add validated settings for maximum input tokens, response reserve, minimum recent messages, maximum tool-result contribution, maximum context growth per continuation, summary target size, and diagnostic logging. Effective input budget is the lower of configured maximum and known model context window minus requested output allowance/reserve. Unknown window sizes remain explicitly unknown. Estimate the exact final protocol body using current estimators where applicable, with a documented safety margin; expose estimates as estimates. If the request cannot fit while preserving pinned content, return a clear budget error containing counts and remediation rather than silently deleting user instructions or sending an oversized request.

The manager checks every actual upstream attempt after provider transport changes, not just the initial client turn. A growth limit is enforced only when FCC has a trustworthy session identity; otherwise report it unavailable rather than treating unrelated requests as one conversation. Derive a privacy-safe identity from explicit session metadata/header when supported, with content-root hashing scoped to the same provider/model as a fallback; never persist raw prompts in telemetry.

### Summaries and reuse

When over budget, first remove exact duplicate tool outputs within the visible history, then compact completed older spans while retaining entire tool transactions. Keep recent turns (at least configured minimum, extended to a valid transaction boundary) byte-for-byte where feasible. Retain user instruction messages intact unless a structured summary can preserve them without losing relevance; because relevance cannot be proven for free text, the initial policy pins explicit instructions and recent user messages and puts older user requirements into structured summary fields without deleting their source from persistent history.

Use a structured summary with fields for current task, requirements/preferences/constraints, decisions, paths/files, changes, important errors and fixes, pending work, and tool-result references. Generate it using the selected provider/model through a bounded internal request, validate the schema, and count its usage. Failed/invalid summary generation leaves the source context intact and results in an explicit over-budget failure. Never resummarize already summarized source spans: maintain content-addressed summary checkpoints keyed by source-prefix digest, protocol, model/provider, policy version, and stable instruction digest. Reuse a matching checkpoint byte-for-byte; only summarize newly appended source spans. Keep checkpoint storage bounded and separate from original conversation persistence. A checkpoint is derived context, not proof that referenced tool output is retrievable.

Preserve stable prefixes byte-for-byte whenever possible. Only reconstruct instructions/tools when the provider adapter requires it, and then preserve their order and cache-control metadata. Each compaction pass must demonstrate a strict decrease in estimated input or mark source spans/checkpoints as consumed; cap passes and summary calls per outbound request. If a pass fails schema validation, yields no size reduction, repeats an input digest, or reaches the cap while still over budget, stop immediately and return an explicit diagnostic. Do not retry compaction in a loop.

Tool output handling is conservative: exact repeats can reference the first retained occurrence; oversized text can keep head/tail, errors, paths, and structured identifiers only when enough evidence remains for the current task. Do not claim a path or ID is retrievable unless an existing tool/store can retrieve it. Keep call/result IDs paired and preserve order. If a necessary result cannot be safely shortened, pin it and allow the request to fail the budget check.

### Cache-aware layout and observability

Repeated FCC calls often keep most of the prompt and vary only a small suffix. Treat preserving provider prompt-cache hits as a first-class optimization alongside reducing total input. The user's Google Billing report for Nov 1–8 showed 426,613 normal input counts and 126,758 cached input counts (about 77% normal and 23% cached); this is the baseline to improve, while the separate Monitoring total remains unreconciled. Keep the serialized system/developer instructions, stable tool schemas, and any reusable compacted task state at the front in an invariant order and representation; place chronological conversation items after them, with the newest changes at the end. Preserve required chronological order within conversation history and never reorder opaque reasoning/signature items. Do not rebuild or normalize an unchanged prefix on every request. Record a digest/version for the stable prefix (scoped to provider, model, protocol, and policy version) so diagnostics can identify why it changed. Never share cached task state across users or authorization/session boundaries.

Compaction can improve the following requests' cacheability: create a compacted checkpoint at a safe completed-turn boundary, then reuse that exact checkpoint while appending later turns. Do not repeatedly rewrite the checkpoint as small changes arrive. If over-budget compaction must replace a previously sent prefix, report that as a cache reset; correctness and budget limits take precedence over a cache hit. Do not manufacture cache-control flags in generic transports. Preserve existing provider cache metadata. Implicit caching in Gemini and Vertex favors large common content at the start and similar requests sent close together; the Google documentation states the cached prefix can be evicted earlier than its maximum lifetime ([Gemini context caching](https://ai.google.dev/gemini-api/docs/caching), [Vertex context caching](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/context-cache/context-cache-overview)). Keep this optimization active for generic/fallback requests. Explicit Google resources are created and used only by the native adapter described above. Likewise, use each other provider's documented prefix/cache semantics rather than assuming one generic cache policy works everywhere.

Keep provider cached-token counts separate from total input, uncached input, local summary-checkpoint hits, and explicit cache creation/storage. Phase one measures the existing implicit-cache path before explicit cache creation is enabled. For Gemini/Vertex, capture actual uncached and cached input usage when returned and track repeated stable prefixes with a keyed digest scoped to the authenticated session, without storing prompt text or raw session IDs; reconcile aggregate token counts with Google billing/SKU data for the same project/model/time range. The storage-cost baseline for currently absent explicit caches is zero; estimate candidate explicit-cache creation and TTL storage charges from Google's current published rates and cache token counts, and label those projections clearly. Phase two records actual native generation usage metadata, cache resource creation and expiry, cache token count, TTL/storage cost, and realized break-even; generic Chat fallbacks consume cached counts if present and keep them unknown when omitted. Record per upstream attempt: protocol/provider/model, stable-prefix digest/version and whether it changed, explicit cache reference state (without exposing it to clients/logs), estimated input before/after, estimated savings, retained message/item counts, tool-output bytes/tokens, internal summary calls, and actual input/cached/output/total usage when returned. Derive cache-hit fraction and realized savings only from actual usage/cost data; mark them unavailable when the provider omits required fields, then compare aggregate diagnostic totals against the Google billing SKU report over the same project/model/time window. Once a response completes, compare estimator values to provider usage and record signed delta and relative error by protocol/model/token class; never rewrite actual usage with estimates. Emit structured diagnostic logs without raw message contents. Aggregate actual usage across attempts without double-counting cumulative stream snapshots. Extend Admin usage by provider/model with observed calls, actual normal input, actual cached input, cache-hit/reuse rate, estimated cache creation/storage cost, modeled net savings, and output; keep estimated cost visually distinct from usage totals and show a negative net result. Explicit cache activation requires a trustworthy session scope and is refused otherwise.

### Integrity and failure behavior

Do not modify source request/history or persisted code-session transcript. Preserve chronological order among retained messages. Validate provider tool-call/result invariants after each adapter. Preserve opaque encrypted/signature-bearing records when safe conversion is unknown. If a provider payload uses server-side history that FCC cannot inspect, report the visible estimate as incomplete. Budget failures must be explicit, actionable, and occur before the upstream call.

## Test and measurement plan

Add unit/transport tests for: short histories unchanged; long histories with structured compaction; recent-message preservation; old decisions in summaries; large tool outputs; duplicate tool results; valid call/result grouping for all three protocols; provider-specific extension/signature preservation; repeated over-budget retries/continuations; task continuity from summaries; idempotent reuse of summarized spans; cache-stable prefix preservation; explicit cache create/reuse/expiry/roll-forward/fallback, cache-vs-inline non-duplication, and model-ineligible behavior; baseline measurement and activation gate; cost break-even; estimate versus API usage calibration; and no-progress/maximum-pass loop protection. Include native passthrough and internal web-search requests. Add deterministic same-history before/after token-estimate benchmarks using the repository's estimators and report both estimated savings and known estimator limits. Tests must verify the original request and SQLite history remain unchanged.

## Implementation sequence

1. Add failing tests and a deterministic protocol-neutral compaction model.
2. Implement budget settings, robust estimates, safe tool-grouping, structured summaries, bounded checkpoint reuse, and explicit failure behavior.
3. Add hooks to each final transport send, native Messages passthrough, internal calls, and retries/continuations.
4. Wire actual usage and per-attempt context diagnostics into existing stream accounting.
5. Run focused tests, the full relevant suite, and the same-history benchmark; inspect regressions in the dirty worktree without overwriting existing changes.

## Implementation status and verified limits (2026-11-08)

- Implemented on feature branch `codex/intelligent-context-management`. Configurable budgets and reserves live in FCC settings; the manager uses model window metadata when available.
- Summary checkpoints use a private SQLite sidecar at `~/.fcc/context-checkpoints.sqlite3`, capped at 512 entries and storing only digested keys and structured summary JSON. A store-recreation test confirms idempotent reuse. Original API history and code-session persistence are unchanged.
- Focused verification: 322 tests passed; additional API regression groups passed 318 and 145 tests. `compileall` and `git diff --check` passed. PyYAML was installed in the local venv; full collection still has three Vertex/Google imports blocked by the Termux cryptography ABI and the browser smoke module requires Playwright (excluded from Android dev dependencies). A broader run excluding those four modules was stopped at 32% after 2,663 passed and 16 pre-existing Android Claude launcher fixture failures (`am` missing from the mock). The previously failing API regressions passed after fixing cross-context `ContextVar` reset.
- Anthropic usage telemetry reads nested `message_start.message.usage`, reports cached and uncached counts separately, and compares the estimate against total input when all cache fields are known.
- Deterministic benchmark: estimated input 9,167 -> 223 tokens (97.6% reduction; 8,944 estimated tokens saved), messages 30 -> 7. It uses a canned summary and therefore does not measure summary quality or actual provider billing.
- Final-send hooks cover the shared Anthropic Messages, OpenAI Chat, and OpenAI Responses transports, including retries/continuations routed through them. Direct native CLI egress is outside these hooks. Growth-limit state is per ProviderExecutor, scoped by auth/session, and capped at 512 entries.
- Context preparation is installed and reset around each awaited provider stream advance to respect ASGI task context boundaries.
- Custom providers that bypass the three shared transports need an explicit allowlisted integration or a documented unsupported diagnostic; never imply universal enforcement unless covered.
